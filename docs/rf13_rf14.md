# RF-13 y RF-14 — Administración de roles y rectificación

Documentación de las dos funcionalidades nuevas del SVDM.

## Cuentas de demostración

| Usuario | Contraseña | Rol operativo | Administrador TI |
|---|---|---|---|
| `u-admin` | `demo` | Sin rol operativo | **Sí** |
| `u-sinrol` | `demo` | Sin rol | No |
| `u-analista` | `demo` | Analista | No |
| `u-aprobador` | `demo` | Aprobador | No |

`u-admin` sirve para mostrar que los permisos de administración son **técnicos**: puede gestionar cuentas, pero **no aprobar** consolidaciones. La aprobación exige el rol `aprobador`.

## RF-13 — Administración de roles

### Modelo

La tabla `users` ahora tiene:

- `role`: `analista`, `aprobador` o `NULL` (sin rol operativo);
- `is_admin`: 0 o 1.

Los cambios se leen en cada solicitud desde la base, no desde la cookie. Por eso una asignación o revocación se aplica en la **siguiente solicitud** del usuario afectado, aunque mantenga la sesión abierta.

### Endpoints

| Método | Ruta | Permiso | Descripción |
|---|---|---|---|
| GET | `/api/admin/users` | administrador | Lista cuentas, rol operativo y flag de administrador |
| PATCH | `/api/admin/users/:id` | administrador | `{ role, is_admin, reason }` |

`role` acepta `analista`, `aprobador` o `null`/`sin_rol`.

### Reglas

- Solo un administrador puede consultar o cambiar roles.
- El administrador no puede cambiar su **propio rol operativo** (evita autoasignarse privilegios).
- No se puede dejar el sistema sin administrador: si se intenta quitar el último `is_admin = 1`, responde 409.
- Una cuenta sin rol operativo recibe 403 en las rutas de negocio.
- El administrador sin rol operativo **no puede aprobar**; la aprobación exige `aprobador`.
- Cada cambio guarda en `audit_events`: actor, fecha, cuenta afectada, valor anterior, valor nuevo y motivo.
- La interfaz **Administración** está visible solo para administradores.

### Cómo probarlo en la web

1. Entrar como `u-admin` / `demo`.
2. Abrir **Administración**.
3. Editar `u-sinrol`, asignar `analista` y escribir un motivo.
4. Cerrar sesión y entrar como `u-sinrol`: ya puede usar las vistas de negocio.
5. Volver a `u-admin`, quitar el rol y comprobar que `u-sinrol` recibe “Cuenta sin rol operativo” en su siguiente solicitud.

## RF-14 — Rectificación de una consolidación aprobada

### Modelo

La tabla `consolidations` ahora tiene:

- `version`: número consecutivo por cliente y período;
- `supersedes_id`: versión anterior;
- `is_current`: 1 para la versión vigente;
- `rectification_reason`: motivo;
- `oc_reference`: referencia de OC, si existe;
- `calculation_hash` y `calculated_at`: control de cálculo desactualizado.

Restricciones:

- `UNIQUE(client_id, period, version)`.
- Índice único parcial para **una sola versión aprobada vigente** por cliente/período.
- Índice único parcial para **una sola rectificación abierta** por cliente/período.

### Endpoints

| Método | Ruta | Permiso | Descripción |
|---|---|---|---|
| POST | `/api/consolidations/:id/rectify` | analista | `{ reason }`; crea la versión siguiente |
| POST | `/api/consolidations` | analista | Genera o recalcula; si hay rectificación abierta, recalcula esa versión |
| GET | `/api/consolidations?period=...` | operativo | Todas las versiones del período |
| GET | `/api/consolidations/:id` | operativo | Detalle, versión anterior y `is_stale` |
| POST | `/api/consolidations/:id/submit` | analista | Envía a revisión; bloquea si está desactualizada |
| POST | `/api/consolidations/:id/approve` | aprobador | Activa la versión de forma atómica |
| POST | `/api/consolidations/:id/reject` | aprobador | Vuelve a borrador; la anterior sigue vigente |

### Flujo

1. Una consolidación aprobada queda en `v1`, `is_current = 1`.
2. El analista pulsa **Rectificar**, escribe el motivo y se crea `v2` en borrador, `is_current = 0`, `supersedes_id = v1`.
3. `v1` sigue vigente mientras `v2` está en borrador o revisión.
4. `v2` pasa por envío y aprobación.
5. Al aprobar `v2`, en una transacción se desactiva `v1` y se activa `v2`.
6. `v1` conserva estado `aprobada` y sus líneas; queda como histórica.
7. Si `v2` se rechaza, vuelve a borrador con motivo y `v1` sigue vigente.

### Cálculo desactualizado

Si una lectura cambia después de generar un borrador (por ejemplo, una corrección desde Alertas), el hash de las lecturas ya no coincide. El envío y la aprobación responden 409 hasta que se regenere la consolidación. La interfaz muestra **“Cálculo desactualizado”** y deshabilita el envío.

### OC y Finanzas

Si la versión anterior tiene `oc_reference`, se copia a la nueva. La interfaz la muestra y recuerda que la coordinación con Finanzas sigue pendiente. El alcance termina en la aprobación local.

## Migración

La migración se ejecuta al abrir la base y es idempotente:

- **users**: se reconstruye la tabla para permitir `role` nulo y agregar `is_admin`, conservando usuarios y sesiones.
- **consolidations**: se reconstruye la tabla para agregar versión, vínculo, vigencia, motivo, OC y hash; se elimina `UNIQUE(client_id, period)`.
- Las consolidaciones existentes pasan a **versión 1** y `is_current = 1`, conservando su `id`, líneas, totales, estado y aprobación.
- Se crean los índices únicos de versión, versión aprobada vigente y rectificación abierta.
- Ejecutar la migración dos veces no duplica ni pierde datos.

Los borradores migrados sin `calculation_hash` se consideran desactualizados y deben regenerarse antes de enviarse.

## Recorrido breve para la defensa oral

1. Entrar como `u-admin` y abrir **Administración**: mostrar las cuatro cuentas y sus permisos.
2. Asignar `analista` a `u-sinrol` con un motivo; explicar que el cambio rige en la siguiente solicitud y queda auditado.
3. Entrar como `u-sinrol` y comprobar que ya accede al negocio. Volver a `u-admin`, revocar el rol y mostrar la vista “Cuenta sin rol operativo”.
4. Entrar como `u-analista`, crear y aprobar la consolidación de un cliente; luego abrir **Rectificar**, escribir el motivo y mostrar `v2` en borrador mientras `v1` sigue **Vigente**.
5. Enviar `v2` y aprobarla como `u-aprobador`; mostrar en el historial que `v2` queda **Vigente** y `v1` **Histórica**.
6. Mostrar el bloqueo por cálculo desactualizado: rectificar, corregir una lectura y comprobar que el envío se bloquea hasta regenerar.
7. Cerrar mostrando que `u-admin` no puede aprobar: la administración es técnica; la aprobación exige rol `aprobador`.

## Pruebas

La suite cubre:

- acceso administrativo autorizado y denegado;
- asignación y revocación con sesión abierta;
- auditoría de cambios con antes/después/motivo;
- autoasignación bloqueada y último administrador protegido;
- administrador sin rol operativo no aprueba;
- migración desde el esquema anterior preservando IDs y líneas;
- inmutabilidad de la versión aprobada al rectificar;
- versión anterior vigente hasta aprobar el reemplazo;
- rechazo de la rectificación;
- historial y una sola versión aprobada vigente;
- rectificaciones concurrentes;
- bloqueo de envío de un borrador desactualizado.

## Limitaciones

- No se crean ni eliminan cuentas desde la interfaz; solo se administran roles y el flag de administrador.
- El administrador puede quitarse su propio flag solo si queda otro administrador; la interfaz no expone esa edición para evitar errores.
- `oc_reference` se conserva, pero no hay formulario para ingresarla; se prevé para la integración con Finanzas.
- La coordinación con Finanzas y la emisión de OC están fuera de este alcance.
- La autenticación sigue siendo local; no se integró Entra ID.
- La migración está probada sobre el esquema anterior del MVP, no sobre una base de producción a escala.
